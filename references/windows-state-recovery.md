# Windows 桌面项目状态恢复

## 适用证据与验证程度

2026-11-09 在 Windows 桌面包 `26.1103.4239.0` 的一次本地排查中观察到：应用返回项目列表为空、旧聊天的项目归属为空；SQLite 中原项目、根目录和聊天归属仍在；同一状态库的独立 app-server `project/list` 能读取这些项目。项目配置保存在全局状态的旧账号快照中，当前顶层缺少对应字段。

当时检查应用实现确认：全局 JSON 在启动时读入内存，没有文件变化监听；后续保存会用内存内容覆盖文件。直接修改运行中 JSON 后，修改被覆盖，这条路径已证明无效。随后按该机器的证据准备一次性离线恢复程序，在完全退出后备份最新状态、合并缺失字段并原子写入，读回核对成功。2026-11-20，使用者确认恢复测试成功，同日应用工具确认原项目重新可见。此为单台 Windows 的实际恢复案例，不代表所有版本或平台通过；个人计划、备份和该次离线程序未包含在公开包中。

这些是特定版本观察，并非官方稳定存储协议。版本或结构变化时重新核对；不能据此要求用户降级，也不能直接运行未核对的旧写入脚本。

## 只读定位

默认目录通常是用户的 `.codex`，有 `CODEX_HOME` 时以实际环境为准。先列当前文件，避免推测编号：

- `.codex-global-state.json` 及确实存在的 `.bak`、更早备份。
- 当前 SQLite 状态库。示例版本名为 `state_5.sqlite`，不是跨版本约定。
- 公开应用工具的项目、聊天和归档清单。

SQLite 使用只读 URI `mode=ro`，保持 WAL 可见，不用 `immutable=1` 忽略活跃 WAL。先查 `sqlite_master` 和 `PRAGMA table_info`，再读取项目相关列。不单独复制活跃主库文件当作完整数据库备份；需要数据库备份时使用 SQLite backup API。本类显示修复通常无需写数据库。

独立 app-server 只适合作为必要的只读交叉核对：先用本机实际 CLI 的 help 和协议生成器确认当前方法。已有数据库记录时，不调用 `project/create` 或 `project/import` 来“补显示”。不伪造桌面 renderer 私有 RPC。

## 精确恢复字段

已观察版本使用以下五个项目字段：

```text
local-projects
project-order
thread-project-assignments
thread-project-membership-host-ids
app-server-project-id-by-legacy-project-id-by-host
```

相关账号分区为：

```text
electron-account-renderer-state-v1.owner
electron-account-renderer-state-v1.inactive[owner].globals
electron-account-renderer-state-v1.inactive[owner].atoms
```

`owner` 是本地分区索引，不能把它当登录凭证，不能据此切换认证账号。恢复计划绑定到用户要恢复的目标分区，不把全部旧账号快照合并到所有账号。不同候选数据不一致时，不自动选“最近”或“第一个”。

已观察启动行为会先选择空 owner：

- 磁盘 owner 非空时，顶层账号字段会暂存到该 owner 的 inactive 快照，之后登录再恢复。
- owner 已为空时，顶层账号字段可能被清除；只修复顶层不足以持久生效。

需要写入时，按项目 ID、聊天 ID 和主机映射键逐项补齐目标 owner 的 `inactive[owner].globals`，不能用旧快照整块替换字段或丢弃后来新增的条目。相同项不重复，不同值先解决冲突；顺序保留当前相对顺序。只有磁盘当前 owner 与目标一致时才同步修复顶层。owner 为空或变成其他账号时，不盲写它的顶层配置。无法确认目标分区时先解决该歧义。保留所有 `atoms`、其他分区和无关字段。

若目标快照已经完整而 owner 为空，先核实分区选择与加载原因，不生成没有差异的写入计划；不能通过改写 owner 来强行解决。

## 准备离线写入

从可信快照构造最小计划，内容只包括目标状态文件路径、目标 owner、确认的五字段、证据来源以及计划生成时相关字段的基线。不要把完整全局文件复制进 skill 或公开输出。

将原有字段与恢复内容比较：缺失项可补回；相同项不必改动；如果用户又增加或移动了项目，重新核对合并。遇到同一项目/聊天 ID 的冲突值，停止应用旧计划，不能覆盖新变化。项目名称、目录、排序、旧 ID 到新 ID 的映射都依据真实证据，不自行发明。

写入前检查应用是否仍在运行。进程名在已观察版本为 `ChatGPT.exe`；以实际安装及进程证据为准，不永久硬编码该名字。退出到托盘不算退出。用户允许等待退出时，使用一次性、隐藏窗口的辅助进程，保留日志、状态与取消方式；不要创建永久开机项或重复的后台修复进程。用户关机、重启电脑或等待超时，可能导致程序未执行，必须通过实际状态核对。

可靠写入应做到：

1. 确认应用完全退出后，重新读取最新 JSON，重新检查 owner、字段基线和冲突。
2. 为这一份最新文件创建带唯一时间戳的恢复前备份，记录散列；不要用较早全文件覆盖当前状态。
3. 只合并确认的字段；把拟写结果放在同目录唯一临时文件中，flush 并 fsync。
4. 替换前再次检查应用未启动、原文件与刚读到的内容一致。发生竞争就取消此次替换，重新读取；有限次重试后停止并报告。
5. 原子替换后读回比对，检查修改范围及无关状态保留情况。保留备份，标记“配置已写入，等待重开核验”，停止辅助进程。

后台等待有明确截止时间；失败不得记录成功。避免强制退出应用、中断其他聊天、后台切账号或自动改认证。用户之前已经选择了等待或退出时机，不重复索取相同确认。

## 重开后核验

重新调用应用项目和聊天工具，核对名称、目录、数量、真实 ID 或经过证据确认的 ID 映射、原归属、归档状态。若 JSON 写入成功但界面仍空，检查是否登录了目标分区、字段是否又被覆盖及是否发生版本迁移；先保留证据，不通过重建同名项目掩盖问题。

回滚也要在应用退出且确认无新变化时进行。优先仅撤销本次改动字段；全文件备份仅在不会覆盖后续工作时使用。
